# Sage VS Code development: first complete slice

Date: 23 October 2026. Owner approved this written specification on 24 October 2026 for implementation planning; **implementation awaits written-plan approval**. Architectural path under brainstorming. This document contains behavior and verification requirements, not an implementation plan. It supplements the [approved foundation](2026-10-22-sage-foundation-design.md) and [accepted delivery direction](2026-10-22-sage-delivery-scope.md) without claiming those approvals cover this new subsystem.

## Outcome and limits

The Windows/macOS portfolio assistant has a JARVIS direction and three demonstrations: development, browser practice and personal organization. This specification delivers the first complete development demonstration: **“build a small focus tracker here”** creates a real tiny project in an explicitly approved empty local folder, shows the actual proposed changes in VS Code, applies the reviewed files, runs a separately approved real test process, opens the result, and completes a later existing-file change while preserving intervening human edits.

The new-project outcome is required here. The first slice is deliberately a dependency-free focus-tracker project; arbitrary repository scaffolding and arbitrary test runners are later capabilities. A deterministic proposal fixture proves the workflow without an account; a usable live Copilot coding adapter separately requires the live acceptance described below. Neither alone proves the entire demonstration.

Only one explicitly paired, trusted, local, single-folder VS Code window is supported per Sage desktop instance. The owner chooses a disposable local empty folder and opens it in a **new local VS Code window** before pairing. Sage does not navigate, reuse, close, reload, install into, or change settings in an existing SSH window. Remote/WSL/container/Codespaces, web, virtual and multi-root workspaces are refused, even if the extension happens to execute locally. Workspace changes and extension reloads revoke pairing. VS Code documents that workspace extensions may run on remote machines; local extension placement alone therefore does not establish a local workspace. [Remote extension architecture](https://code.visualstudio.com/api/advanced-topics/remote-extensions).

The project consists of exactly four ordinary top-level files: `index.html`, `focus.js`, `focus.test.mjs`, and `README.md`. HTML uses a classic relative script, so the tracker can open directly from disk without a development server, module loader or package installation. The tracker supports a named focus session, start/pause/reset, elapsed time, completed sessions and a total during the current page session; refreshing resets it and the UI/README says so. Persistent tracker history, analytics, network dependencies, login and cloud storage are outside this small first project. `focus.js` separates testable state/time calculations from browser presentation. The test file uses Node's built-in test/assert facilities. The follow-up changes one selected existing file per reviewed job; multiple sequential follow-up jobs are allowed.

Non-goals: arbitrary native coding-agent tools, repository search, arbitrary file operations or filenames, dependency installs, shell/task execution, Git mutation, browser automation, publish/deploy/push, messaging, general desktop control, additional providers, a local-model implementation, voice authorization, and restart-resumable automation. These limits keep this slice complete without making Sage a general localhost execution service. Other provider/local-model support remains required later in the accepted delivery scope.

## Approach selection

| Approach                                        | Assessment                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Paired loopback data bridge; recommend**      | Standard Node TCP/crypto in Electron main and the local extension. One authenticated channel carries context, proposals, state and receipts. File/test effects require a local VS Code review gesture and cannot be invoked by a bridge message. Smallest common Windows/macOS implementation without a native dependency. Requires careful application authentication and explicit local-process threat limits.                  |
| OS-local socket on macOS, named pipe on Windows | Useful namespace isolation and filesystem permissions on macOS, but different cleanup and permission semantics. Node supports both transports but its public `net` API does not supply a custom Windows security-descriptor parameter. A user-specific Windows DACL/peer verification requirement would need additional native implementation or a reviewed dependency; do not infer it from a pipe name or `readableAll: false`. |
| Extension owns the entire assistant             | Removes the cross-app channel, but duplicates Sage provider, routing, task and approval ownership and does not provide the approved Sage desktop workflow. Defer this independent product direction.                                                                                                                                                                                                                              |

Node documents Unix socket/Windows pipe differences and its exposed listening options. Windows default named-pipe access is a separate OS security concern, not a property Sage may assume from the transport label. [Node IPC](https://nodejs.org/api/net.html#ipc-support), [Windows named-pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).

## Ownership and user flow

Electron/React remains Sage's presentation; its sandboxed renderer never gains Node, bridge keys, filesystem paths-as-commands or a generic IPC passthrough. Electron main owns the paired endpoint. The existing supervised Python core owns routing policy, coding job identity/state, model invocation, approval bindings and durable receipts through the existing private framed IPC. Long jobs use start/status/cancel and correlated progress; an individual RPC stays within the existing 30-second bound. Do not turn one RPC into the whole human review interval.

A Sage-owned local VS Code extension owns its native context picker, read-only diffs, apply/save controls, the narrow test process and opening a known result. Its native review controls receive no command/URI arguments that authorize effects. Incoming bridge data may offer a proposal for review, update a status or acknowledge a journal record; it cannot call apply, save, execute a command, launch a process, open a URL or fetch source. VS Code commands used internally are a fixed reviewed allowlist, never model/bridge-selected names. The extension and other installed local extensions execute with the user's editor privileges; malicious extensions or a compromised trusted host are outside the isolation this protocol can provide.

1. In Sage, choose **Pair local VS Code**. In the intended local window, invoke Sage's pairing command, enter the displayed ephemeral ticket, and verify the same folder/window challenge in both applications. Confirm the exact destination in Sage; no source is shared by pairing.
2. Select **Create focus tracker in this empty folder** in the extension. Sage shows the destination, the four permitted filenames, the bounded user request, coding provider/account/model/destination, quota disclosure and **Send request**. No model call occurs until this explicit disclosure decision. The extension checks that the destination is empty, including hidden entries; `.git`, `.vscode` and prepared starters make it nonempty. Sage never empties a folder for the user.
3. A powerless coding adapter returns a structured proposal. VS Code opens original/proposed read-only diffs and a file manifest. Creation diffs show empty baselines. Sage may summarize, but the actual extension diffs and full source are the review surface. The user reviews and chooses **Create these four files**. Decline/cancel creates nothing.
4. The extension records and performs only that approved effect, then reports observed per-file outcomes. On verified creation, select **Run focus tests**. A separate review displays the exact test authority below and requires **Run once**. No apply approval includes permission to run code.
5. Show the actual exit result and bounded output in VS Code and a receipt/status in Sage. **Open result** opens the known `index.html` or selected changed source in the paired window. A separate **Open tracker in browser** click opens only this project's verified `index.html` file URI in the OS default browser. This runs the reviewed HTML/JavaScript; neither a proposal nor test completion opens it automatically. Observing the running tracker is required before claiming the demonstration works.
6. For a follow-up, the user saves any human edits normally, selects one existing target and any other explicitly shared manifest files, and submits a new request. A fresh snapshot and new approval replace the old context. No prior provider session, previous approval or old diff is reused as authority. A human modification between jobs appears in the new baseline and survives the follow-up.

The extension declares no support in Restricted Mode and checks `workspace.isTrusted` at every sensitive transition. Trust is a prerequisite for executing reviewed workspace code, not an OS sandbox or blanket test approval. [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust).

## Decision 1: authenticated cross-app transport

Use a raw TCP listener bound explicitly to **127.0.0.1**, an OS-selected ephemeral port, only while pairing/paired. No `localhost` resolution, wildcard interface, HTTP server, WebSocket, CORS endpoint, URI handler carrying credentials or network discovery. TCP is only the transport for the closed data bridge; there is no execution method on the wire.

The trusted host generates a random boot ID and 256-bit one-use pairing secret. Its ticket contains only protocol version, port, boot ID and secret, is shown only on explicit pairing, expires after 60 seconds and is never persisted or logged. The extension accepts it through a password-style local input; no automatic clipboard write, shell argument or workspace file stores it. Both endpoints authenticate fresh nonces, boot ID, extension activation/window ID and canonical local root identity with HMAC-SHA-256. Verify the host proof before releasing context. The paired folder identity and a short challenge are displayed in both UIs for the user's confirmation. Derive a session key from the secret and both nonces, then erase the ticket secret from application state. The ticket cannot pair a second window.

Each direction uses a length-prefixed UTF-8 envelope with closed version/kind, boot/pair/window/job IDs, monotonically increasing sequence, payload and MAC over exact framed payload bytes. Reject MAC failure, unknown fields/kinds, wrong identity, repeated/out-of-order sequence or payload over 1 MiB before dispatch. Use constant-time MAC comparison. Handshake timeout is 10 seconds, at most two unauthenticated sockets and one paired socket, and at most eight pending authenticated frames per direction; overflow closes the channel and stops new effects. Authentication failures return no workspace/account details. No source-bearing broadcasts. No automatic reconnection; disconnect closes the endpoint and requires fresh pairing. Revocation, app quit, cancellation-induced disconnection and either application's restart invalidate all session credentials and unconsumed approvals.

The channel authenticates possession of the pairing secret, not an OS-attested application binary. It does not defend against a local administrator, process-memory access, a stolen ticket or a malicious extension in the same host. Loopback traffic is not claimed encrypted. Avoid remote/forwarded environments, and disclose this local trust boundary. Accepting this residual risk for the explicitly paired portfolio slice is proposed here and remains pending the owner's written-spec review and adversarial authentication evidence; no such acceptance permits a general localhost API. `net` provides explicit host binding and random-port listening; cryptographic protocol behavior remains a Sage requirement to verify. [Node network API](https://nodejs.org/api/net.html).

## Decision 2: bounded source disclosure and a powerless coding adapter

Introduce separate closed coding values alongside the note contracts; do not widen `notes.create`, `Approval` scope or `ReasoningResult` into arbitrary actions. A coding request binds job/request/cancellation IDs, boot/pair/window/root IDs, mode (`create_focus_project` or `replace_focus_file`), selected backend/model/account destination, user text, deadline, context revision and the exact disclosure hash. Provider-visible file records use relative manifest names and text, not absolute local paths, usernames or a workspace scan. Local receipts retain the root binding needed for reconciliation.

For follow-up the user picks 1–4 manifest text files; only one is writable. Include whole clean saved UTF-8 documents with LF and no BOM in this slice, not silent selections of an unseen whole file. Other encodings/EOLs, dirty/open-conflicted documents and external changes produce an explanation and require the user to resolve/save or choose another target. Never convert or save a document just to make it eligible. Capture URI/root identity, editor version, logical content hash, disk-byte hash and file identity/stat for local validation. Optional diagnostics are separately selected, previewed and counted; they can themselves contain source/private text. No clipboard, terminal output, environment, Git diff, hidden files, instructions, chat history, open tabs or diagnostics are attached automatically.

Limits: one active coding job, user text at most 32,000 Unicode code points, at most four source records, at most 32,000 code points per file, and 64,000 code points total attached source plus selected diagnostics and provider-visible metadata. Structured output has the same per-file/64,000-total text limits, exactly the four create records or exactly one replacement, and a 2,000-code-point explanation. Preserve foundation literal-text validation, allowing tabs/newlines but rejecting NUL, unsupported controls and invalid Unicode. Serialized messages must also fit 1 MiB. Reject oversize input/output without truncation or secondary fetch. Inference has a 120-second deadline, cancellable independently of review. A review expires after five minutes; source/proposal memory expires after 30 minutes even if the UI stays open.

The first live capability is **Copilot structured code proposals**, using the pinned supported SDK/runtime and supported Sage account acquisition already owned by the foundation. It is independent of ordinary reasoning readiness and returns data only: explanation plus the exact permitted filenames/replacement contents. Unknown fields, commands, tool calls, paths outside the manifest, duplicate filenames, malformed JSON and disallowed text are errors, never instructions to an executor. Use constrained output where supported and strict validation regardless.

Reuse the existing empty-mode policy, zero built-in/custom tools, denied permission handler, disabled skills/hooks/MCP/subagents/ambient discovery and disposable Sage-owned session filesystem. The working directory is Sage's disposable provider area, never the project. A fresh session sees only this job's approved snapshots; it cannot read or alter the workspace. No VS Code token extraction, private Copilot APIs or attachment to the owner's existing chat/session. Empty mode and explicit tool registration are documented controls; actual enforcement must be proved against the pinned combination. [Copilot SDK isolation guidance](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/multi-tenancy), [built-in skill exclusion](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/skills).

**Local AI only** refuses cloud coding before auth/session/inference and never falls back. Until a reviewed local coding adapter exists, model-backed coding shows unavailable; deterministic fixtures remain test infrastructure, not an advertised local model. Readiness checks and pairing do not send a synthetic prompt. Live connection/coding tests require a new explicit bounded consent; previously consumed one-test approvals do not revive. Optional paid cloud remains a separate visible choice, not a prerequisite silently enabled by editor sign-in.

## Decision 3: exact review, creation, stale edits and saving

Approvals are separate `code.create`, `code.replace` and `code.test` grants, issued by trusted state after a local review decision. They bind the whole normalized proposal/test specification, original/proposed hashes, exact filenames/root/window/pair/job, revision, policy version, boot and five-minute expiry. Revision, backward-clock anomaly, cancellation, disconnect, changed scope/content/config or restart invalidates the grant. A duplicate decision yields its existing known receipt only after binding validation. Consume once and durably record intent before effects. The extension cannot treat a model string or renderer-supplied object as approval.

**Create:** require the explicitly approved root to remain the same canonical ordinary directory and still empty immediately before starting. All four names are fixed simple basenames; reject path separators, case aliases, detected symlinks/junctions/reparse targets, hardlinked existing targets, UNC paths, non-`file` URIs and known network mounts. The owner must explicitly confirm that the destination is on a local disk they control; mapped/network filesystems and concurrent hostile directory replacement are unsupported. Node's portable API is not treated as proof that an arbitrary mapped volume is local or every Windows reparse type is detected. Do not follow a model path or create nested directories. Recheck root identity and cancellation between files. Create each file with exclusive non-overwriting open (`wx`), write its approved UTF-8 bytes through the owned handle, close and read back. Existing targets cause refusal, never overwrite. Node documents exclusive creation and warns it may not work on network filesystems; this is why local-disk eligibility is explicit. [Node file flags](https://nodejs.org/api/fs.html#file-system-flags).

Creation is **not a four-file transaction**. Before each create, durably record that filename as starting; afterward record the actual existence/length/hash or failure. On collision, partial write, close/read-back failure, cancellation or receipt loss, stop remaining creates and show `partial` or `needs_reconciliation` with the per-file facts. Preserve already created files and any concurrent user's file; never clean up, delete or retry automatically. Recovery is an explicit inspect-and-new-request operation. Exclusive open prevents overwriting an existing same-name file; it does not prove protection against hostile concurrent replacement of ancestor directories. This slice assumes the owner controls the approved local destination; an adversarial local filesystem actor is outside its containment claim.

**Replace:** support exactly one existing manifest document per job, with no resource creation/rename/delete in that proposal. Show original/proposed read-only text through a content provider and the documented diff command, plus EOL/encoding and exact content hashes. Require the target to be clean, same URI/file/root identity and same disk hash before the local apply decision. Obtain the actual `TextEditor`, then recheck version/content/dirty state and cancellation synchronously inside `TextEditor.edit`'s callback before adding its one whole-document replacement. There is no asynchronous gap between that final callback check and registering the replacement. The documented edit transaction checks intervening document changes; handle `false` as a stale/failure result. Do not rely on a prior hash check followed by an unversioned filesystem overwrite. [Text editor API contract](https://raw.githubusercontent.com/microsoft/vscode/main/src/vscode-dts/vscode.d.ts), [documented diff command](https://code.visualstudio.com/api/references/commands).

Editor auto-save must be off for the target while this reviewed effect is pending; if the user's effective setting enables it, refuse and explain the requirement without changing their settings. After successful edit, verify the live buffer equals the approved proposal before requesting that document's save. Never `saveAll`, force overwrite, revert, auto-merge, auto-undo or write replacement bytes directly to disk. If another edit appears, stop the automatic save and leave the user's buffer visible. Existing editor undo remains the user's choice.

Saving is a separate observed step within the explicit **Apply and save this file** decision, not an atomic transaction with editing. Save participants, formatters or another extension may change text; a human can also edit while the save is pending. Record the save response and reread the live buffer and disk. Only clean buffer plus matching approved byte hash is `applied_saved`. A failed save is `applied_unsaved`; a changed/uncertain result is `needs_review`/`needs_reconciliation`, preserving the current document and actual hashes. Show the difference from the approved proposal and require fresh review/context before testing; never repair it with another write. VS Code's API does not promise an edit/save transaction. [VS Code document/save API](https://code.visualstudio.com/api/references/vscode-api).

Editor-version races must refuse stale replacements in real extension-host tests. Disk checks and save conflict handling reduce accidental external-editor conflicts; they do not establish a cross-process compare-and-swap filesystem transaction. A save already dispatched cannot be recalled reliably. Cancellation stops subsequent steps and records any in-flight save result without undoing it. If the supported editor/runtime fails the stated stale-editor race criteria, disable replacement readiness until corrected; do not substitute an unfounded atomicity claim.

## Decision 4: concrete test authority and cancellation

The first and only test action is **Run focus tests once**. The extension owns a fixed process recipe, not `tasks.json`, task providers, a terminal command or a model-provided string. The user selects an already installed standalone Node executable outside the workspace through a local file picker; resolve its canonical absolute path, record identity/hash and obtain its version through a separately disclosed bounded `--version` check. Match the repository's supported range, **Node >=26.12.1 and <27, stable releases only**; older versions, including the owner's measured 26.10.0, are ineligible. Node 26.12.1 is the initial validation target; a later eligible patch/minor becomes ready only after this exact recipe/environment passes the platform acceptance checks and that exact version is recorded. A range match alone is not validation. This follows the maintained floor and security release, without requesting an older global runtime. [Node 26.12.1 security release](https://nodejs.org/en/blog/release/v26.12.1/). Selecting an executable authorizes this version probe, not a project test; no runtime download or package install occurs. VS Code/Electron's own `process.execPath` is not assumed to be a standalone Node installation.

After verified saved effects, preview the absolute executable and identity/version, fixed argv `--test --test-isolation=none --test-reporter=tap focus.test.mjs`, canonical cwd, deadline, output cap and environment policy/map, distinguishing explicit empty values from omitted keys. The current official Node 26.12.1 documentation supports these flags and the built-in TAP reporter; no test-runner child is needed with isolation disabled. [Node CLI test isolation](https://nodejs.org/api/cli.html#--test-isolationmode), [Node built-in reporters](https://nodejs.org/api/test.html#test-reporters). Approval binds all four current saved project hashes, the executable hash/identity and this exact recipe/environment; recheck immediately before spawn and refuse a changed/dirty file or binary. There is still a cross-process check/use race, not a sandbox guarantee.

Use `spawn` with an argv array, `shell: false`, detached false, stdin closed and captured stdout/stderr. Reuse the tested explicit-blank policy of `desktop/main/child-env.ts` for the extension's narrowly owned recipe; do not introduce a broader environment abstraction or inherit the parent map. An absolute executable needs no search path, so `PATH` is explicitly empty on both platforms. Set `TEMP`, `TMP` and `TMPDIR` to a fresh extension-owned temporary directory. On Windows preserve only the validated OS-location values `SystemRoot`, `WINDIR` and `SystemDrive`, and explicitly set `HOME`, `HOMEDRIVE`, `HOMEPATH`, `LOGONSERVER`, `USERDOMAIN`, `USERNAME` and `USERPROFILE` to empty strings; `HOME` is also explicitly blanked even though it is not in libuv's current required-variable list. Reject ambiguous case aliases and emit one canonical key per case-insensitive name. On macOS omit identity/home keys; retain only the existing boundary's explicitly allowed OS-root carryover if present. `NODE_OPTIONS`, `NODE_PATH`, authentication/proxy/cloud variables and workspace environment overrides are absent from the constructed map. Use this policy for the disclosed version probe as well as the project test.

Omission is not claimed to prevent Windows identity inheritance: libuv fills missing required slots from the parent, including `USERPROFILE` and home-directory components. Explicit blank entries prevent that fallback in the tested boundary. [libuv Windows environment construction](https://raw.githubusercontent.com/libuv/libuv/v1.x/src/win/process.c). Preview the final constructed spawn map including empty values, and disclose any known native additions established by the supported platform checks. Readiness requires an actual child-environment fixture under the relevant packaged extension host to verify that previewed empty/omitted distinctions hold and synthetic ambient identity/secret values do not leak; do not call an unmeasured supplied map the effective environment. This is an environment-minimization policy, not process containment. No hooks, setup command, task dependency, background/watch mode, glob, `.cmd`/`.bat`, command substitution, auto-install or fallback executable. Remove only Sage's own temporary directory after the run; never project files.

This executes reviewed **project code with the current user's authority**. The test can access files/network and spawn descendants; a reduced environment and trusted workspace do not contain it. The UI says this before Run once. Sage does not claim to prevent a malicious approved test from downloading/installing things. Sage itself dispatches only the fixed process, never install/network/publish commands. Generated tests being green do not prove the generated app correct; independent acceptance checks and running-app observation are required.

Bound a run to 30 seconds and 256 KiB combined output; capture at most that amount, mark overflow and terminate the direct child. Render output as inert text with terminal/control escapes removed, never clickable command links or HTML. Output is local/session-only and is not automatically supplied to the provider. Exact raw output is not written to ordinary logs. Result binds execution ID, start/end times, project hashes, process identity, exit code/signal, timeout/cancel/overflow and an output digest. Only a correlated observed exit 0 with no timeout/cancellation/overflow and unchanged project hashes is `passed`; nonzero is `failed`, mutation is `changed_during_test`, signal/null/missing exit is `cancelled` or `unknown` as applicable.

Cancel/timeout closes stdin and signals the owned live child once; after two seconds it may request force termination of that same still-live child, then observes completion for at most three more seconds. Never kill by persisted PID or global process name. If no completion is observed, show `termination_unconfirmed`; do not allow an automatic new test. Node documents that signalling/killed status is not proof of exit and killing a parent does not guarantee descendant termination. No process-tree containment is claimed; an escaped descendant may remain and requires user inspection. [Node child-process termination](https://nodejs.org/api/child_process.html#subprocesskillsignal).

## Decision 5: retention and durable effect receipts

Use existing SQLite task/operation storage for coding metadata; keep source/proposed content/request text/diagnostics/test output only in current memory and disposable provider storage, subject to the 30-minute cap. Drop them promptly on decline, cancel, expiry, terminal completion or disconnect. Do not persist a coding transcript or source archive; follow-ups read fresh explicitly selected files. VS Code itself may retain editor history/local file history under its own settings, and the cloud provider has its own disclosed retention; Sage's policy is not a zero-retention or forensic-erasure promise. Provider disconnect alone does not establish deletion; use and verify the existing owned session filesystem/cleanup lifecycle. [Copilot session lifecycle](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/session-persistence).

Durable records retain job/operation/revision IDs, state/timestamps/policy/provider versions, local workspace/window identity, the four relative filenames, original/proposed/observed hashes, grant hash and expiry/consumption, per-effect intent/outcome and redacted error category. Test receipts retain recipe/environment and executable identity hashes, nonsecret recipe fields, exit/cancel/uncertainty and output digest, not raw output. Absolute root location is private reconciliation metadata and must not appear in telemetry/default logs or provider input. No token, source, note body, user prompt, diagnostics or environment secret belongs in either receipt store.

For cross-app crash recovery, the extension keeps a small versioned effect journal in its private extension global storage, outside the project, with the same source-free operation IDs/intents/observations. It must durably acknowledge an intent locally and in core before starting a new effect. It journals observations locally before sending them to core; core acknowledges durable recording. There is no atomic transaction spanning SQLite, the extension journal and editor/filesystem/process effects. Failure to persist intent means zero new effects; failure after an effect means uncertainty rather than retry. Enforce one writer/job for the root and no second pairing to the same Sage instance; this serializes Sage, not human editors or unrelated processes.

Delete terminal metadata and extension receipts after 30 days. Interrupted/uncertain operations remain inspectable during that period with an expiry warning; expiry removes metadata, never workspace files or processes. Approved sources remain the user's ordinary project files. Journals are not encrypted by this design; use per-user application storage and disclose normal OS account protection. Reuse foundation migration/future-version refusal and redacted errors; no new orchestration framework or source database is needed.

## Decision 6: cancellation, restart and reconciliation

Coding states are `context_ready`, `proposing`, `review_required`, `applying`, `applied_saved`, `applied_unsaved`, `needs_review`, `test_review`, `testing`, `completed`, `rejected`, `cancelled`, `failed`, `partial`, `interrupted`, and `needs_reconciliation`. Receipts hold finer per-file/process facts. A cancelled job may still have committed files; terminal wording must show those facts instead of implying rollback. Provider output after cancellation/revision never reopens review or applies anything.

Cancellation invalidates pending grants and prevents new inference/create/edit/save/test/open steps. Abort provider work through the supported lifecycle and discard late results. Allow an already dispatched create/edit/save to settle, record what occurred, and stop before the next effect. A test that has begun follows the explicit termination rules. Disconnect requests the same stop; bridge loss is not permission to continue. Report cancellation requested while cleanup is pending, and cancellation/termination unconfirmed when provider or process shutdown cannot be observed. Never claim work stopped merely because the UI no longer accepts its results; late results remain unusable even when the remote provider's final state is unknown.

On either app restart, all unfinished jobs are interrupted, pairing/approvals expire and no provider request/edit/save/test/browser open resumes automatically. Do not start LangGraph replay for this slice. A fresh paired local window can offer **Inspect interrupted job**: compare the exact journal's root/files and current disk hashes locally, checking any open buffers as well. Missing versus original/proposed/other hashes classify current observations; they do not prove who wrote a file or recover historical causality. Display `observed proposed content; completion receipt missing` when that is all that is known. Human-modified content stays untouched. Without original/proposed bodies there is no recoverable old diff; a new request must obtain new context and new approval.

Core and extension reconcile by operation ID with journal acknowledgments; conflicting or missing observations remain `needs_reconciliation`. If the process receipt is lost, mark test outcome unknown even if files look correct; never rerun automatically or infer test success. After extension-host crash, do not attempt to terminate a persisted PID that may have been reused. Warn that an earlier process/descendant may remain. The user may acknowledge inspection and start a new job, which grants no retroactive success to the old one.

## Acceptance and security evidence

Tests use disposable folders/user-data, deterministic provider doubles and synthetic private markers. They must assert actual effects and zero forbidden calls, not reassuring text. These criteria are implementation-independent; file-by-file work, packaging commands and dependency pins belong in the subsequent approved implementation plan.

1. **Required new-project demonstration:** begin with a genuinely empty approved folder, submit “build a small focus tracker here”, inspect four real creation diffs, approve creation, verify exact files/bytes and receipts, separately approve the Node test and observe its true result, open the result in the paired VS Code window, and explicitly open/observe the working browser tracker. Independently exercise start/pause/reset, completion/total and the disclosed refresh reset. No starter project, dependency installation, network service or provider account is needed for the deterministic workflow acceptance.
2. **Follow-up:** make a human edit after the first job, save, share fresh context and change one selected existing file. Its actual diff includes that baseline; the human change and unrelated files survive. Independently inspect behavior instead of relying only on generated tests. Display unavailable accurately when a selected mode/provider is not implemented.
3. **Editor race/save:** real extension-host tests edit between review/apply, during the final edit request and during save, undo/redo, change disk externally, enable auto-save, add a save participant, fail saving and close/reopen the editor. Stale editor replacements perform zero stale writes; intervening human buffer changes survive. Changed save results never become successful approved-byte receipts or start tests. Explicitly record the limits of cross-process disk races.
4. **Creation interruption:** collision after approval, nonempty destination, same-name/case collision, symlink/junction/escaped root, wrong filesystem/encoding, partial-write failure, disk-full/permission failure, cancellation after each file and crash before/after each receipt. No existing target is overwritten or deleted; no automatic rollback/retry occurs, and all partial/uncertain effects remain visible.
5. **Disclosure/bridge:** wrong/expired/replayed ticket, forged host/client proof, second window, wrong boot/root/job, malformed/MAC-invalid/oversized/replayed/out-of-order messages, HTTP/browser probes, queue overflow and disconnect produce zero unauthenticated source release or forbidden effects. Remote, untrusted, virtual/multi-root and nonlocal destinations are rejected. A bridge proposal cannot invoke native operations; no generic read/execute endpoint exists.
6. **Authority:** deny, expiry, replay, stale revision/content/config, cancelled grant and concurrent Sage job yield zero effect calls. Note approval cannot authorize code or tests.
